# SimpleScrollの設計見直し

使い方のシンプルさと高いパフォーマンスを設計の基準とする。移動管理の重複を解消した後、公開APIとGridの可視セル表現を見直し、その上で対象4種へのoffsetとduration追加を進める。

## 移動管理

Scrollerが現在位置、目標位置、速度、移動状態を管理する。各Scrollはレイアウトから目的地を計算し、LazyLayoutは追従するindexとanchorを保持する。

- 停止はScrollerの目標位置、速度、保留中の移動量をまとめてリセットする。
- Idleでは補間しない。慣性移動から境界へ戻る動きはSnappingとして扱う。
- レイアウト補正は現在位置と目標位置を一緒にずらす。
- ドラッグ、ホイール、スクロールバー、直接の位置指定、無効化で以前のセル追従を解除する。
- 更新処理で配列、LINQ、クロージャ、コルーチンを新規に作らない。セルの仮想化とプールを維持する。

全Scrollで停止するStopと、CarouselのSnapToNearestを分離する。旧StopScrollはObsolete警告付きで残し、Carouselの従来のスナップ動作を維持する。移行方法は[API移行ガイド](api-migration.md)を参照する。

### LazyLayoutの追加課題

実測サイズ40、推定サイズ100の10セルで、Refresh(1f)の最初の計測後にSetPositionIndex(0, smooth: false)で先頭へ戻すと、前方セルを補充するループでindexがマイナス1になり範囲外参照が発生する。前方補充の境界と位置補正を別途修正する。正規化位置の要求保持とは別の未解決課題として扱う。

## 公開APIと非推奨化の課題

移動管理の変更では、従来のprotected UpdatePositionの引数付きオーバーロードを薄い転送として残し、Obsoleteで引数なしUpdatePositionとMoveToPositionへの移行を案内する。既存の継承コードは警告付きでコンパイルできる。旧APIは1.xでは削除せず、2.0で削除する予定とする。

Stop、SnapToNearest、SetNormalizedPositionを実装し、旧StopScrollを非推奨化する。位置指定付きRefreshは正式APIとして維持する。その他のAPIの方針は以下のとおり。

| 現行API | 見直し内容 |
| --- | --- |
| SetPositionIndex | indexがデータindexなのか表示位置なのかを明確にする。Carouselのループ位置との違いも定義する |
| SetScrollPosition | index指定と同じ移動管理を使い、直接位置指定の単位と符号を定義する |
| smooth引数 | duration追加時に即時移動と時間指定へ整理する。現在の追従係数を秒数へ直接変換しない |
| StopScroll | StopとSnapToNearestへ分離済み。旧動作は互換入口として維持する |
| Refreshのオーバーロード | 位置指定付きRefresh、Refresh(bool)、SetNormalizedPositionを用途別の正式APIとして維持する。更新と表示位置の指定を一度に行えるようにする |
| VisibleRangeとOnVisibleRangeChanged | 非連続の可視indexを正確に扱うAPIへ移行する |
| protectedのRepositionとUpdatePosition | 継承する利用者も移行対象とし、公開メソッドと同じく変更手順を定義する |
| IndexedDictionaryなどの補助型 | 1.xでは公開を維持する。内部化は2.0で判断する |

置換先が使える状態になってから、旧APIにObsoleteの警告と移行例を追加する。単に警告だけを追加しない。同名のoptional引数付きオーバーロードによる曖昧さと、既存の引数省略時の動作変更を検証する。互換処理は旧APIから新APIへの薄い転送に限定し、削除するバージョンを決める。

## Gridの並び順と可視セル

現在はRepositionの戻り値、VisibleRange、変更イベント、CellViewPool.ReleaseOutOfRangeがすべてStartからEndまでの連続indexを前提にしている。さらにGridの配置とSetPositionIndexは、スクロール方向に沿って連続するindexを並べる計算になっている。戻り値の型だけを変更しても、並び順の切り替えには対応できない。

例として、可視セルが0、1、5、6、10、11の場合、Rangeの0から11では非表示セルまで含まれる。

対応する課題は以下。

- スクロール軸と、行を先に埋めるか列を先に埋めるかを分離する。
- 行数と列数をどのように決めるかを定義する。現行のColumnは横スクロール時に交差軸の個数として使われるため、単純な名前変更では既存シーンの意味が変わる。
- データindexと行・列の変換を、配置、サイズ計算、index指定移動で共通に使う。
- 可視indexを正確に列挙・判定できる値型を検討する。連続区間と規則的な複数区間を小さな記述子で表し、毎フレームの配列生成や全データ走査を避ける。
- プールは可視セルだけを走査し、可視集合から外れたセルだけを解放する。判定用のクロージャを毎フレーム作らない。
- VisibleRangeを単なる最小・最大indexの包絡区間として残す場合、正確な可視集合と混同させない。旧イベントも非推奨化の対象とする。
- Repositionは戻り値だけではオーバーロードできない。新しいprotectedメソッド名による段階移行か、メジャーバージョンでの変更を選ぶ。
- 横・縦スクロールと行優先・列優先の全組み合わせ、端の未充填行・列、実行中の切り替え、セル再利用、可視集合の通知をテストする。

新しい可視集合API、Gridの設定名、互換期間は未決定。Gridの並び順切り替えはまだ実装していない。

## 性能の確認

機能テストと性能測定を分ける。定常スクロールのGC割り当て、表示セル数に対する更新時間、表示セル数と生成セル数を比較する。停止中のScrollerは早期returnするが、データ更新やレイアウト確認まで停止させない。高いパフォーマンスを数値で保証するには、対象端末と実際のセルを使ったProfiler計測が必要。

## 実施順序

1. 移動と停止の責務を整理し、回帰テストを通す。
2. 停止・スナップ・正規化位置のAPI分離と、1.xでの警告付き互換維持、2.0での旧API削除を移行方針とする。
3. 可視index表現とプールを見直し、Gridの並び順切り替えに対応する。
4. Carouselを除く4種へoffsetとdurationを追加する。
5. サンプル、README、移行例、性能測定を更新する。
